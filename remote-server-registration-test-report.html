1 Cmdlets in the flow

Local · COM

Get-StorageSyncServer

Reads local server identity & state through the Azure File Sync agent.
  • Server ID, server role (Standalone / ClusterNode)
  • Cluster ID & name (for cluster nodes)
  • Agent version & OS version
  • Managed-identity Application ID & Tenant ID
In: none  ·  Out: PSLocalStorageSyncServer
Remote · ARM

Register-AzStorageSyncServer

Creates the registered-server resource in Azure using managed identity.
  • Generates a new ServerId (deterministic in tests)
  • Sends ApplicationId, AgentVersion, ServerRole
  • No certificate, no RBAC, no local calls
  • Runs from any workstation or automation host
In: RG, Service, ApplicationId, AgentVersion, ServerRole  ·  Out: PSRegisteredServer
Local · COM

Connect-StorageSyncServer

Persists the registration on the local server from Azure-returned values.
  • Takes ServerId, ServiceUid, endpoints, locations
  • Validates identity & discovers cluster config
  • Writes registration into the local agent
  • No second Azure create call
In: explicit scalars from step 2  ·  Out: PSRegisteredServer

6 Why the split matters

🔀

Remote and Local are cleanly separated. The remote cmdlet touches only Azure Resource Manager and can run from anywhere. The local cmdlets touch only the on-box Azure File Sync agent through the COM IECsManagement interface and must run elevated on the server.

The three commands share no objects and are not piped — the operator carries plain values between them. This makes remote registration possible from a management host while local persistence stays on the target server.
