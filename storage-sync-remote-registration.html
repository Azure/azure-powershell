Proposed command architecture

Azure File Sync remote registration

Split the existing mixed registration workflow into an Azure-only resource command and a local-only agent connection command. The Azure command runs first; its output is transferred to and consumed on the target server.

Command responsibilities

Local / Azure File Sync agent

Get-StorageSyncServer

  • Runs locally on the Windows Server that has the Azure File Sync agent installed.
  • Reads the local server ID and, for cluster nodes, the cluster ID and cluster name through COM.
  • Reads the server system-assigned managed identity application ID and tenant ID.
  • Read-only; creates or modifies nothing in Azure or on the server.
  • Returns PSLocalStorageSyncServer for the operator to inspect.
Remote / Azure Resource Manager

Register-AzStorageSyncServer

  • Runs from an administrator workstation, automation host, or other remote environment.
  • Accepts the Storage Sync Service and managed identity ApplicationId.
  • Creates a new ServerId GUID before the Azure Resource Manager request.
  • Uses managed identity mode implicitly; there is no Identity switch.
  • Calls the Microsoft.StorageSync registered servers REST API.
  • Does not invoke local COM APIs, create certificates, or assign RBAC roles.
  • Returns PSRegisteredServer whose values the operator supplies to the connect step.
Local / Azure File Sync agent

Connect-StorageSyncServer

  • Runs locally on the Windows Server that has the Azure File Sync agent installed.
  • Accepts explicit scalar parameters that the operator copies from the register step's output.
  • Uses ISyncServerRegistration orchestration over the existing COM interface.
  • Treats the Azure-returned server ID as authoritative and validates the managed identity application ID.
  • Discovers standalone or failover cluster role, cluster ID, and cluster name through COM.
  • Persists the Azure response into the local FileSyncSvc configuration.
  • Does not create or update the Azure registered server resource.

Three independent steps

The three commands are independent and are not connected through the pipeline. The operator reads values from step 1 and supplies them as explicit parameters to steps 2 and 3.

Step 1 (local)

Read local info

Get-StorageSyncServer

Reads server ID, cluster role, cluster ID, cluster name, and managed identity application ID through COM.

→
Step 2 (Azure)

Register remotely

Register-AzStorageSyncServer

Creates a new ServerId GUID and the registered server resource in Azure. Returns service endpoints, StorageSyncServiceUid, and locations.

→
Step 3 (local)

Connect locally

Connect-StorageSyncServer

Takes the Azure-returned values as explicit parameters and persists the registration through COM. No pipeline handoff and no second Azure create call.

Service GUID stitching

The remote cmdlet generates ServerId, while Azure generates and returns properties.storageSyncServiceUid on the registered server resource. The first command exposes this value as PSRegisteredServer.StorageSyncServiceUid. Connect-StorageSyncServer receives it through the explicit StorageSyncServiceUid parameter, constructs the internal registration model, and passes it into ISyncServerRegistration.Connect.

The local registration client parses the value as a non-empty GUID and calls IECsManagement.PersistSyncServerRegistration with the GUID in the existing storageSyncServiceUid COM parameter. The COM interface remains unchanged.

Validation and failure behavior

Before Azure registration

  • ServerId and ApplicationId must be non-empty GUIDs.
  • The Storage Sync Service resource ID must be valid.
  • -WhatIf prevents the REST operation.

Before local persistence

  • The Azure File Sync agent and monitoring path must exist.
  • The local managed identity tenant must match the Azure context tenant.
  • The local flow uses the Azure-returned server ID and does not call GetSyncServerId.
  • Local and remote application IDs must match.
  • Cluster role, cluster ID, and cluster name are discovered locally and merged before persistence.
  • COM failures remain explicit ServerRegistrationException errors.
Key design constraint: IECsManagement remains unchanged. The split is implemented in the PowerShell cmdlets and the managed ISyncServerRegistration orchestration layer.
